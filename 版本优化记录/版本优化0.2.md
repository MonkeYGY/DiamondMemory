# 版本优化 V0.2

### 1. 语义检索支持短期记忆（L1/L2）
- **修改文件**: `backend/app/services/retrieval_service.py`
- **优化内容**: 修改了 `_semantic_search` 和 `search_by_tags` 的过滤逻辑，将原先仅允许检索 L3-L6 层的限制放宽至 L1-L6。这使得外部 AI 软件（如 OpenClaw）能够通过语义匹配直接回溯到最近的原始对话碎片，彻底解决了“短期记忆失忆”的问题。

### 2. 检索结果增加上下文前缀标识（防污染机制）
- **修改文件**: `backend/app/services/retrieval_service.py`
- **优化内容**: 在 `_format_results`、`search_by_tags` 和 `search_recent` 等方法中，为返回给外部 AI 的 `content` 动态注入了层级标识前缀。
  - L1/L2 数据标注为：`[近期短期记忆 / 未经整理的对话碎片 (L1/L2)]：`
  - L4-L6 数据标注为：`[长期核心经验 / 结构化知识 (L4-L6)]：`
  - 其他数据标注为：`[目录或索引 (L3)]：`
- **优化目的**: 帮助外部 AI 在获取混合记忆时明确感知数据的“生熟程度”，防止将短期口水话与长期真理混淆，避免产生逻辑幻觉和人设偏移。

### 3. 本地大模型算力保护（微批处理机制）
- **修改文件**: `backend/app/services/memory_service.py`
- **优化内容**: 为核心的自动提炼方法 `process_l1_to_l2`、`process_l2_to_l4`、`process_l4_to_l6` 引入了 `batch_size` 参数（L1->L2 限制20条，L2->L4/L4->L6 限制5条）。
- **优化目的**: 替代了原本的“全量取出、同步阻塞循环”逻辑。现在每次触发整理时，只会处理一小部分积压数据，有效防止本地大模型（如 Ollama）因长时间满载而导致的系统卡顿或 OOM（内存溢出），完美契合“后台延时微批处理”的架构思想。

### 5. 解除本地大模型上下文限制并引入“双向动态阶梯内存分配”
- **修改文件**: `backend/config.py`、`backend/app/config/settings.py`、`backend/app/services/inference/inference_service.py`、`backend/app/services/memory_service.py`
- **优化内容**:
  1. 将系统默认的最大 `LLM_CONTEXT_SIZE` 和 `local_llm_max_tokens` 从 `4096` 提升至 `128000`。
  2. 修复了调用 Ollama API 时缺失 `num_ctx` 参数的问题。
  3. **【核心优化一】引入动态阶梯上下文分配 (`_calculate_dynamic_context`)**：在发给 Ollama 前，系统会根据输入文字的长度（字数 * 1.5 + 预留输出），智能计算当前任务需要的最小上下文窗口，并在 `2K, 4K, 8K, 16K, 32K, 64K, 128K` 这个阶梯中自动选择。
  4. **【核心优化二】引入动态输出长度分配 (`dynamic_output_limit`)**：针对长文本总结容易被固定 `max_tokens`（如 2000 或 6000）截断的问题，在 `memory_service.py` 中引入了基于输入长度动态计算输出上限的逻辑。例如，合并总结时输出上限为 `max(3000, 输入字数 * 0.8)`，既保障了短文本的快速生成，又为万字长文（如 17KB 的 Markdown）预留了充足的输出空间，彻底告别总结被强行掐断的问题。
- **优化目的**: 
  - **解决长文截断Bug**：动态放大输出上限，使得模型能完整吐出万字长文的详细报告。
  - **解决爆内存问题**：如果一刀切地每次都强行开启 128K 的上下文窗口或超大的输出上限，KV Cache 会瞬间吃掉大量的统一内存/显存。采用“双向看菜下饭”的动态分配后，日常处理短文本时只占用极小的内存（2K-4K），使得这套系统在低配电脑上依然能流畅运行。

### 6. 模型管理支持接入外部商用大模型与成本控制
- **修改文件**: `backend/app/config/settings.py`, `backend/app/api/config_routes.py`, `backend/app/services/inference/inference_service.py`, `backend/app/services/memory_service.py`, `DiamondMemory/Modules/Mine/ViewModel/ModelManagementViewModel.swift`, `DiamondMemory/Modules/Mine/View/ModelManagementView.swift`, `DiamondMemory/Common/Tool/ModelStatusManager.swift`, `DiamondMemory/Modules/Home/View/QACenterView.swift`, `DiamondMemory/Common/Config/AppConfig.swift`
- **优化内容**:
  1. 在设置页面（模型管理）新增了“大模型接入方式”的分段选择器，支持在“本地模型 (Ollama)”和“外部商用大模型”之间无缝切换。
  2. 为外部模型配置提供了预设的商用模型下拉菜单，并支持输入 `Base URL` 和 `API Key` 的可视化配置表单。提供了**测试连接**按钮。
  3. 后端 `InferenceService` 增加了外部大模型（OpenAI 兼容接口）的请求路由逻辑。并在后端新增了**统一流式聊天接口 (`/inference/chat/stream`)**，无论是本地还是外部大模型均支持流式输出。前端 `QACenterView.swift` 的直连 Ollama 逻辑已被重构为请求后端统一流式接口，彻底解决了外部大模型回复缓慢的问题。
  4. 修复了切换云端模型后状态栏未正确更新的 Bug，模型状态管理器 (`ModelStatusManager`) 现可精准感知外部提供商的状态。
  5. 新增外部大模型的 Token 消耗流量统计功能，每次调用后累加 `total_tokens` 并在前端 UI 实时显示。
  6. **【新增成本控制隔离逻辑】**：在 `memory_service.py` 中增加了对外部大模型的专属费用保护逻辑。当检测到当前使用的是按 Token 计费的 `external` 外部大模型时，其提炼任务的最大输出限制将不再盲目挂钩于 `local_llm_max_tokens`（如 128k），而是安全降级为 `external_llm_max_tokens`（默认 8192），在保证输出完整性的同时，彻底防止天价账单和无意义发散。
  7. **【新增全局大模型总开关】**：在模型管理顶部新增了 `启用大模型处理` 开关。如果用户选择关闭，系统将安全降级为**纯向量检索模式**（自动中止 L2->L4 和 L4->L6 的大模型提炼流转，对话时仅返回检索内容），实现0消耗数据存储。
  8. **【新增三级自动降级容灾机制 (Auto Fallback)】**：
     - 当处于**外部商用大模型**时，如果发生网络超时、API Key 欠费或连接错误，系统会自动将 `llm_provider` 降级为 `ollama` (本地模型)，并在对话中提示用户。
     - 当处于**本地模型 (Ollama)** 时，如果检测到 Ollama 进程未启动，或者当前本地模型未下载（例如用户没有安装任何模型），系统将自动把大模型总开关关闭（`llm_enabled = False`），彻底降级为**纯向量检索模式**。
  9. **【解耦界面选择与模型激活】**：前端的 `大模型接入方式` 分段选择器现已改为仅切换配置面板视图。只有用户点击下方的“保存并启用”或在列表中点击“切换”，才会真实修改后台的 `llm_provider`，避免了误触导致的自动切换问题。
  10. **【修复免打扰与自定义文件管理逻辑】**：
      - 修复了在知识库界面切换文件“免打扰 (bypass_ai)”状态时，由于 YAML Frontmatter 正则匹配错误导致的“文件解析失败 (The data couldn't be read because it is missing)”问题。
      - 修改了用户自建 Markdown 文档的整理逻辑：开启 `免打扰` 的用户文档在被后台读取并直接作为 L4 经验存入数据库后，**不再强制从用户目录中删除或移动**。源文件将原封不动保留，同时数据库中生成 L4 向量索引；未开启免打扰的文档则正常流入 L1 等待后续大模型提炼流转。
  11. **【根除 Mock Summary 脏数据污染】**：在底层的 L2->L4 提炼逻辑中加入了 Mock 数据拦截器。如果大模型输出的总结文本中含有无效的占位符（如 `Mock summary` 或 `MockCategory`），系统将主动拒绝将其写入数据库，并将该条 L2 记录保持为 `pending` 状态以待后续重试。彻底杜绝了无意义空记忆污染知识库的问题。
  12. **【知识库结构深度自清洁机制 (`cleanup_empty_categories`)】**：在 `memory_service.py` 中新增了全面的结构清理算法，并在每次执行知识库同步（或手动整理）结束时自动触发。该机制不仅能精准定位并抹除数据库中所有孤立的、没有子记忆的空分类记录（L3/L5），还会使用 `topdown=False` 的算法深度扫描文件系统，物理销毁所有残留的空文件夹和 Mock 脏目录，彻底告别了知识库列表里长满空分类的顽疾，保证了系统的极度整洁。
  13. **【史诗级架构重构：Batch RAG (增量检索聚合) 流水线】**：
      - 彻底重构了 `memory_service.py` 中 `L2->L4` 和 `L4->L6` 的提取循环逻辑。不再是低效的串行逐条提问，而是引入了全新的 **Batch RAG** 模式。
      - 系统现在会将积压的多条待处理新记录组合，并通过向量数据库提前召回所有相关的旧知识（上下文），将它们组装成一个带有严谨 JSON 输出约束的单一巨型 Prompt，一次性发送给大模型（如云端 API）。
      - 大模型站在“上帝视角”进行批量的合并、新建与分类。后端在收到 JSON 后自动拆分、覆盖和分发。此举将整理耗时从几十秒/上百秒直接缩短至几秒，API Token 费用和调用次数断崖式下降。
      - **高可用降级 (Fallback) 保障**：如果在批量处理时遇到大模型返回 JSON 解析失败或网络断开等问题，系统不会崩溃，而是会自动回退到传统的“逐条迭代处理机制”，保证了极端情况下的提炼可靠性。
  14. **【RAG 检索层级加权 (Layer Bonus)】**：修复了聊天对话框中 AI 只能检索到“版本迭代”等文件标题（L3目录层）而无法读取详细正文（L4经验层）的严重 Bug。在 `retrieval_service.py` 的多路召回计分阶段引入了层级加权机制：给予 L4（总结）和 L6（技能）**2.0 倍**的最高分奖励，给予 L1/L2（原始细节）**1.5 倍**奖励，而对毫无正文价值的 L3/L5 目录层施加 **0.05 倍**的严厉惩罚。此举确保了 AI 助手在检索上下文时能精准、稳定地拉取到详实的核心知识，而不是被高匹配度的标题目录误导。
  15. **【修复 L1 无法沉淀至 L2 的去重 Bug】**：修复了通过 OpenClaw 自动摄取的长篇新闻简报或本地 Markdown 文件，在整理时被莫名标记为“已归档”却未生成 L2 沉淀记录的问题。原因为底层全局配置 `dedup_threshold`（去重阈值）被错误设置为了极低的 `0.6`，导致任何包含通用词汇的中文长文本在进行向量匹配时都会被误判为“已存在的重复记忆”而被系统强行丢弃。现已将该阈值恢复至安全的 `0.85`，保障了新增记忆能顺畅流入提炼管道。
  16. **【全量知识库深度整理机制 (`organize_entire_knowledge_base`)】**：重构了点击“手动整理记忆”时的后端触发逻辑。从原本的“只处理新摄取的待处理记录”升级为**真正的全库扫描与优化**。现在的整理流程包含六个严密的环节：1. 质量清理（删除极短碎片、占位符废话等低质量记忆及文件）；2. L4 经验全量去重合并；3. L6 技能全量去重合并；4. 增量提炼（处理新增的 L1->L2, L2->L4）；5. 全量修正（将未归档的记录重新智能分配分类）；6. 结构清理（物理删除所有空分类记忆和空文件夹）。此举使得系统不仅能处理新数据，还能像硬盘碎片整理一样，越整理知识库越干净、知识点越聚拢。
  17. **【解决大模型批处理失败与同步阻塞问题】**：
      - **动态打包 (Chunking by size)**：重构了 `process_l2_to_l4` 和 `process_l4_to_l6` 的批处理逻辑，抛弃了死板的“按条数打包”（如 5 条/10条），改为使用**动态字符累加策略**。系统现在会在保证单批次字符总数不超过安全边界（如 4000 字符）的前提下，智能决定每次打包的条数。彻底杜绝了打包万字长文导致大模型输出 JSON 被截断的 Bug，完美适配按次收费的云端 API，最大化每次请求的价值。
      - **多线程并发回退 (Async Fallback)**：如果遇到极端情况仍发生 JSON 解析失败并触发回退机制，系统不再使用原先缓慢的“同步串行阻塞”方式逐条处理，而是启用了 `ThreadPoolExecutor` 进行多线程并发提炼（默认 3 并发）。这不仅大幅加快了处理速度，也解决了后台整理时由于单线程阻塞导致的系统和 UI 卡顿假死问题。
      - **下调去重阈值**：将 L4 和 L6 层的全局去重合并相似度阈值从 `0.65` 进一步下调至 `0.55`。有效解决了“多条总结经验描述同一件事却未能合并”的遗留问题，使得知识点更加聚拢。
  18. **【引入检索后去重 (Post-Retrieval Deduplication)】**：
      - 针对外部 AI（如 OpenClaw）在检索时可能拉取到大量 L1 层重复“原始碎片”导致 Token 浪费和上下文污染的问题，在 `retrieval_service.py` 中引入了一道内存级的轻量过滤器 `_post_retrieval_dedup`。
      - 当系统通过混合检索召回包含 L1/L2 数据的候选列表时，过滤器会对这些低层级数据进行**余弦相似度极速对比**（阈值 0.85），剔除其中语义极度重复的“孪生”垃圾碎片，仅保留最新和最完整的记录。同时，L3-L6 核心经验则会被无条件放行。
      - 此举使得发给外部 AI 的上下文变得**高浓度、无重复**，既拥有了过目不忘的 L1 细节记忆，又屏蔽了冗余的垃圾流。
- **优化目的**: 满足商业化高阶需求，通过接入如 MiniMax m-2.5 等能力更强、上下文更长的商用大模型，彻底根治本地小模型的“假提炼”与 JSON 解析失败问题。同时结合严格的 Token 成本隔离保护、流式生成和容灾降级机制，提供极度稳定和丝滑的交互体验。
