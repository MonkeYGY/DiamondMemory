# 启动链路与模型后台预热设计

## 背景

当前应用在开发模式和正式版中都存在相似的启动体验问题：

- 用户点击启动后，前端窗口不能第一时间出现
- 后端、Ollama 和模型加载之间存在串行等待，导致整体可用时间被拉长
- 右上角两个状态点的语义过于粗糙，无法准确表达“未启动 / 已启动但未热加载 / 已热驻内存”的差异
- 用户感知上容易误以为模型没有工作，或者认为软件本身启动很慢

已确认的核心目标是：

- 前端窗口优先显示，尽量做到“打开软件后立刻看到面板”
- 后端、Ollama 和大模型在后台继续启动与预热
- 模型预热采用后台全速并行策略
- 右上角两个状态点改为红 / 黄 / 绿三阶段表达
- 开发模式和正式打包版统一采用同一套体验语义

## 目标

- 缩短“点击启动 -> 前端窗口出现”的主观等待时间
- 将“界面出现”与“服务就绪 / 模型就绪”彻底解耦
- 让后端服务可用后立即开始并行预热主 LLM 与 `bge-m3`
- 让前端状态展示准确反映服务和模型的真实阶段
- 避免重复触发多份预热任务，防止资源浪费与状态混乱

## 非目标

- 这次不改动聊天、检索、整理等业务逻辑本身
- 这次不引入新的外部进程管理器或系统级守护机制
- 这次不做“低功耗预热”或“按需预热”分支策略，统一按后台全速预热执行

## 方案

### 启动原则

- 首屏显示优先于后端与模型就绪
- 服务启动与模型预热使用后台异步任务推进
- 状态展示以“阶段感知”为准，而不是简单的“端口通不通”
- 开发模式与正式版共享同一套状态语义和预热流程，只在启动入口上做环境适配

### 开发模式启动链路

- 调整 `DM开发辅助/open_dev_mode.sh`
- 启动时优先拉起 Electron dev 侧窗口链路，不再等待后端虚拟环境准备完成后才启动前端
- 后端环境检查、虚拟环境修复和源码后端启动继续在独立终端后台执行
- 目标是点击“开发模式”后先看到前端窗口，再等待后端与模型状态逐步从红变黄再变绿

### 正式版启动链路

- `frontend/src/main/index.ts` 保持 `createWindow()` 最优先执行
- `frontend/src/main/backend-manager.ts` 不再让 `startBackend()` 阻塞在 `await startOllama()`
- 将现有启动过程拆成三个后台阶段：
  - `startBackendProcess()`：负责启动后端进程并等待健康检查通过
  - `ensureOllamaService()`：负责确认或拉起 Ollama 服务
  - `warmupModels()`：负责在服务就绪后并行预热主 LLM 与 `bge-m3`
- 三个阶段由主进程统一调度，但不阻塞窗口创建和前端渲染

### 后端预热策略

- 保留 `backend/main.py` 中基于后台线程的模型预热思路
- 预热触发条件改为“后端启动完成且检测到 Ollama 可达”
- 主 LLM 与 `bge-m3` 继续并行预热
- `bge-m3` 统一使用正确的 embedding 预热端点，不再混用文本生成端点
- 若用户在预热完成前先发起聊天或检索，真实请求应复用当前加载中的模型，不再额外开第二份预热任务

### 状态模型

- 右上角两个状态点统一改为三阶段：
  - 红：未启动或不可用
  - 黄：服务已启动 / 模型已安装，但尚未热驻内存
  - 绿：模型已确认热加载到内存，可直接响应
- 第一个状态点表示 `BGE-M3`
- 第二个状态点表示“当前主模型”
- 状态文案示例：
  - `BGE-M3 未启动`
  - `BGE-M3 预热中`
  - `BGE-M3 已就绪`
  - `qwen3.5:4b 未启动`
  - `qwen3.5:4b 预热中`
  - `qwen3.5:4b 已就绪`

### 状态来源

- 前端不再直接仅依赖 `Ollama /api/tags` 结果推断全部状态
- 后端提供聚合后的模型状态接口，统一返回：
  - `backend_ready`
  - `ollama_ready`
  - `llm_installed`
  - `llm_loaded`
  - `embedding_installed`
  - `embedding_loaded`
  - `llm_model_name`
  - `embedding_model_name`
  - `warmup_phase`
- `warmup_phase` 用于表达当前处于：
  - `idle`
  - `starting_services`
  - `warming_up`
  - `ready`
  - `degraded`

### 已加载判定

- “已安装”与“已加载”必须分开
- 已安装：模型出现在 Ollama tags 列表中
- 已加载：模型出现在 Ollama ps 或等价运行态检查结果中
- 对 `bge-m3` 和主 LLM 都采用同样的判定原则，避免一个看安装、一个看运行导致 UI 语义不一致

### 并发与去重

- 主进程和后端都可能参与服务拉起与预热，因此必须有幂等控制
- 同一时刻只允许一份 Ollama 启动流程
- 同一时刻只允许一份模型预热流程
- 若已有预热任务在执行，新的触发方应复用当前任务状态而不是重复启动

## 前后端分工

### Electron 主进程

- 管理窗口优先创建
- 管理后台阶段调度
- 负责开发模式与正式版的差异化启动入口
- 在必要时将阶段状态同步给前端

### Python 后端

- 提供统一的模型状态聚合接口
- 在服务生命周期中维护当前预热状态
- 输出可轮询的预热阶段信息
- 负责实际的模型预热动作与结果落地

### Vue 前端

- 轮询聚合状态接口，而不是自己拼接多份探测结果
- 将两个状态点渲染为红 / 黄 / 绿三阶段
- 在后端未完全就绪时允许界面先可见、先可操作非模型相关区域

## 边界处理

- 若用户当前配置为外部大模型模式，则本地主模型状态点不进入预热流程，文案需反映“使用外部模型”
- 若 Ollama 已安装但未运行，状态应显示黄或红，并明确是服务未就绪而非模型缺失
- 若主模型已安装但 `bge-m3` 未安装，则两个状态点允许分开表现，不强行同步
- 若 Ollama 可用但预热失败，状态应停在黄或降级状态，并暴露失败原因给日志，不阻塞界面继续使用
- 若开发模式后端虚拟环境首次安装依赖较慢，前端窗口仍应优先出现

## 影响范围

- 修改 `DM开发辅助/open_dev_mode.sh`
- 修改 `frontend/src/main/index.ts`
- 修改 `frontend/src/main/backend-manager.ts`
- 修改 `frontend/src/renderer/App.vue`
- 修改 `frontend/src/renderer/components/TopNav.vue`
- 修改 `backend/main.py`
- 修改 `backend/app/api/config_routes.py`
- 视实现方式可能补充后端状态管理模块或复用现有配置 / 服务层

## 验证

- 开发模式下，点击“开发模式”后前端窗口明显早于后端完全就绪出现
- 正式版下，应用打开后窗口立即显示，不再等待 Ollama 或模型预热完成
- 后端启动完成后，主 LLM 与 `bge-m3` 能并行进入预热
- 两个状态点按红 -> 黄 -> 绿逐步变化，且状态与实际运行情况一致
- 未安装模型、未启动 Ollama、外部模型模式、预热失败等场景下，状态文案和颜色仍然正确
- 不会重复启动多份 Ollama 服务或多份模型预热任务
