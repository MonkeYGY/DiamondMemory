# L3/L5 分类归并与 L4/L6 文档式详情阅读设计

## 背景

当前快速整理与深度整理虽然已经能把内容提升到 `L3-L6`，但在“分类收敛”和“阅读体验”两个环节上还没有达到系统设计目标。

现状主要有两个问题：

- `L3/L5` 会持续生成重复或近似分类，例如只是在措辞、后缀、表达粒度上有差异，但本质上属于同一主题，导致分类树越来越碎，失去归类意义
- `L4/L6` 详情弹窗当前只是对文本做浅层字符串替换，本质上仍接近原始文本预览，标题、列表、分段、引用等结构没有被真正渲染，阅读体验拥挤且不利于长期使用

本次设计的目标不是做大而全的知识树重构，而是在现有架构上补齐两个关键能力：

- 为 `L3/L5` 增加“明显近义自动归并”的标准化能力
- 为 `L4/L6` 增加“文档式阅读”的详情展示能力

## 目标

- 在 `L2 -> L4` 与 `L4 -> L6` 生成分类时，优先复用已有稳定分类，减少 `L3/L5` 的重复和近似分类
- 自动归并仅处理“明显近义”的高置信度场景，避免激进误合并
- 为历史已有的 `L3/L5` 提供一次分类收敛入口，逐步把已有碎片分类并回稳定结构
- 将 `L4/L6` 详情页改为偏文档式阅读界面，而不是原始文本预览框
- 让 `L4/L6` 详情页正确展示标题层级、段落、列表、引用、分隔内容与重点字段

## 非目标

- 不在本次方案中引入完整的“人工审核后再合并”的审批工作流
- 不在本次方案中做分类体系的全量重建或复杂别名管理后台
- 不改变用户手工管理分类的入口，原有分类管理弹窗继续保留
- 不改变知识库目录映射的基本语义，仍保持 `L3/L5` 为目录、`L4/L6` 为 Markdown 文件

## 现状问题拆解

### 分类问题

- 当前 `memory_service` 中的 `L2 -> L4` 与 `L4 -> L6` 会调用 `_generate_category()`、`_generate_skill_category()` 直接使用大模型返回的分类名
- 大模型虽然有命名规则约束，但依然可能产生“主题相同、说法不同”的分类名
- 当前缺少“候选分类名 -> 标准分类名”的归并环节，因此新分类会持续膨胀
- 历史整理结果中的重复分类也没有自动收敛机制

### 详情页问题

- 当前 `MemoryView.vue` 的详情页使用 `renderedContent` 对内容进行简单正则处理和换行替换
- 这种方式无法稳定支持 Markdown 结构化渲染
- 现有详情容器更像“渲染过一点点的纯文本”，不是真正文档阅读器
- 对于长篇 `L4/L6` 内容，用户会看到密集的大段文字，难以快速把握结构

## 总体方案

本方案分为两部分：

- `后端分类标准化归并层`
- `前端文档式详情阅读层`

两者相互独立，可以在实现时分阶段上线，但最终应共同构成完整体验。

## 方案一：L3/L5 分类标准化归并

### 核心原则

- 不在前端通过展示层“假合并”分类
- 不在数据库已经写入后再频繁做补救性重命名
- 统一在“候选分类名生成后、落库前”执行标准化归并
- 只自动处理“明显近义”场景，边界模糊时宁可保守保留

### 处理流程

每次 `L2 -> L4` 或 `L4 -> L6` 生成分类时，采用如下流程：

1. 生成候选分类名
2. 对候选分类名做文本清洗
3. 读取当前层已有分类集合
4. 对候选分类名与已有分类做“明显近义匹配”
5. 若命中高置信度目标分类，则复用已有分类
6. 若未命中，则按清洗后的新分类名创建新分类

### 文本清洗规则

文本清洗只做“降低表达噪音”，不改变主题本体。规则包括：

- 去除首尾空白、重复空格和无意义标点
- 统一中英文括号、连字符、下划线等格式差异
- 统一常见技术词的大小写和常见写法
- 去除明显弱区分后缀，例如“相关”“整理”“总结”“说明”等
- 对“机制/流程/自动化/方法”等相近尾词做轻量归一，但前提是前面的主题主干一致

说明：

- 这一步不是做语义重写，只是让后续匹配更稳定
- 清洗后的“标准比较键”仅用于判断是否归并，不一定直接用于最终显示名

### 明显近义匹配规则

自动归并范围限定为以下情况：

- 主体词完全一致，仅尾词不同
- 主体词一致，仅是否带“自动化/机制/流程/方案/规范”等尾词差异
- 主体词一致，仅复数、修饰词轻微差异
- 技术词与中文短语的常见稳定同义写法

明确不自动合并的情况：

- 两个分类虽然相关，但关注点不同
- 一个偏“写入”，一个偏“同步”
- 一个偏“部署”，一个偏“运维”
- 主题主干不同，只是同属一个更大领域

### 标准分类选择策略

当匹配到多个可能目标分类时，优先级如下：

1. 已存在且被更多 `L4/L6` 使用的分类
2. 命名更短、更稳定、更通用的分类
3. 当前已有文件目录已存在的分类

目标是尽量让系统向“稳定主类名”收敛，而不是每次重新命名。

### 历史分类收敛

除实时归并外，增加一次面向历史数据的收敛入口。

处理流程如下：

1. 扫描所有 `L3` 分类并分组
2. 扫描所有 `L5` 分类并分组
3. 识别出明显近义的分类组
4. 选定一个标准分类作为保留项
5. 将组内其他分类下的 `L4` 或 `L6` 迁移到标准分类
6. 删除空旧分类
7. 同步清理知识库中的空目录

该收敛入口应可独立触发，不要求每次用户操作都自动跑全量收敛。

### 服务边界

- `memory_service`
  - 负责在分类生成路径中接入标准化归并
  - 负责发起历史分类收敛任务
- 新增或扩展一个分类标准化服务
  - 负责分类清洗
  - 负责明显近义匹配
  - 负责标准分类决策
- `md_export_service`
  - 负责分类迁移后对应目录与 Markdown 文件路径同步

### 数据一致性要求

- 数据库中的 `category` 必须与最终使用的标准分类一致
- 知识库目录结构必须与数据库分类同步
- 分类迁移后，`L4/L6` 的 `file_path` 需要同步更新
- 删除冗余分类后，空目录应被正确清理

## 方案二：L4/L6 文档式详情阅读

### 版式选择

本次详情页版式采用用户确认的 `方案 A`，即偏文档式阅读。

设计方向：

- 让 `L4/L6` 更像一篇可阅读的文档
- 保留正文连续性，避免把正文切成大量碎卡片
- 弱化技术实现感，强化阅读感与信息层次

### 结构布局

详情页结构建议为：

1. 标题区
2. 轻量元信息区
3. 正文阅读区
4. 关联内容区（保留现有 `L3/L5` 下层内容能力）

### 标题区

- 使用更明确的文档标题
- 若正文中存在主标题，则优先提取并作为详情页标题
- 否则回退到分类名或当前标题提取逻辑

### 元信息区

保留必要信息，但弱化视觉占比。建议包含：

- 更新时间
- 来源
- 分类
- 标签
- 置信度（若存在）

元信息区不应成为页面视觉重点，避免压缩正文阅读空间。

### 正文阅读区

正文区应支持以下结构化展示：

- 标题层级
- 自然段落
- 无序列表
- 有序列表
- 引用块
- 分隔线
- 粗体强调
- 行内代码或关键信息高亮（可选）

正文区样式原则：

- 行宽适中，避免整行过长
- 行高略大于当前实现，提高长文可读性
- 段间距明显，避免内容粘连
- 列表项之间有足够呼吸感
- 标题与正文之间有稳定层级区分

### 渲染策略

当前前端没有现成 Markdown 渲染依赖，因此实现层有两个候选方向：

- 引入轻量 Markdown 渲染库，并配合基础安全处理
- 在前端实现一个有限范围的 Markdown 渲染器，只覆盖当前 `L4/L6` 常见结构

推荐方向：

- 优先使用轻量 Markdown 渲染库
- 只开启本项目需要的基础语法能力
- 避免为了简单页面渲染维护大量自定义正则规则

### 回退策略

若正文解析失败或内容格式异常：

- 回退为纯文本显示
- 不允许因为渲染失败导致详情页空白

## 组件与代码落点

### 后端

- `backend/app/services/memory_service.py`
  - 在 `_generate_category()` 与 `_generate_skill_category()` 的落库路径前增加标准化归并
  - 为历史收敛提供触发入口
- 新增 `backend/app/services/category_normalization_service.py` 或等价职责模块
  - 负责分类清洗、归并判断、目标分类决策
- `backend/app/services/md_export_service.py`
  - 负责分类迁移后的文件移动、路径重算、空目录清理

### 前端

- `frontend/src/renderer/views/MemoryView.vue`
  - 重构 `renderedContent` 的实现方式
  - 从字符串替换转为真正的 Markdown/结构化渲染
  - 调整详情弹窗样式，使其适配文档式阅读
- `frontend/package.json`
  - 若选用 Markdown 依赖，需要补充对应前端依赖

## 失败处理

### 分类归并失败

- 若标准化服务异常，不阻断记忆生成
- 回退为使用原候选分类名写入
- 记录日志，便于后续排查

### 历史收敛中断

- 单个分类组迁移失败不应阻断整个收敛流程
- 返回成功数、失败数和失败明细
- 迁移失败时不做半删除，避免数据库和文件系统不一致

### 详情渲染失败

- 回退为纯文本展示
- 页面仍可打开、可滚动、可关闭

## 验证方案

### 分类验证

- 快速整理后，相同主题不再持续生成多个近义 `L3/L5`
- 历史重复分类执行收敛后，分类树更稳定、更少碎片
- 收敛后同分类下的 `L4/L6` 仍能正常展示与检索

### 详情页验证

- `L4/L6` 打开后，标题层级、段落、列表、引用能正常显示
- 长文阅读时不再呈现“密密麻麻一整段”的视觉效果
- 正文区滚动表现正常，不影响弹窗交互

### 一致性验证

- 数据库分类、知识库目录、详情页展示三者保持一致
- 分类迁移后导出的目录结构仍符合既有 `L3/L5` 为目录、`L4/L6` 为文件的规则

## 推荐实施顺序

1. 先补齐分类标准化服务与实时归并接入
2. 再提供历史 `L3/L5` 收敛入口
3. 随后改造 `L4/L6` 详情页为文档式阅读
4. 最后做分类迁移与详情页联动验证

## 结论

本方案通过“后端分类标准化归并 + 前端文档式详情阅读”两条改造线，直接解决当前 `L3/L5` 重复近似分类过多，以及 `L4/L6` 详情页过于拥挤的问题。

在实现策略上，本方案坚持：

- 分类归并只处理明显近义，优先稳妥
- 详情页以连续阅读为主，而不是碎片化卡片展示
- 尽量复用现有架构，在当前 `memory_service + md_export_service + MemoryView.vue` 边界内完成演进
