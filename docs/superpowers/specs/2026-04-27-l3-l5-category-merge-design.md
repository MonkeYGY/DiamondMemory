# L3/L5 分类归并设计

## 背景

当前系统已经具备 `L1-L6` 分层整理、知识库目录下行和 `L4/L6` 父级展示能力，但 `L3/L5` 仍会持续产生近义重复分类。

典型问题包括：

- 同一主题因为尾词不同而拆成多个分类，例如“知识库同步”“知识库同步机制”“知识库同步流程”
- 同一技术主题因为命名粒度或表达习惯不同而拆分，例如“OpenClaw配置”“OpenClaw一键配置”“OpenClaw接入配置”
- 历史数据中的重复分类会持续留在知识树中，影响 `L3/L5` 的目录稳定性和长期可读性

现有后端并没有 `L3/L5` 的归并能力。当前深度整理只会处理：

- `L4/L6` 内容去重
- `L4` 默认分类重分类
- 空 `L3/L5` 清理

因此，系统现在能“清空壳”，但不能“收敛近义分类”。

## 目标

- 为 `L3/L5` 增加“只合并明显近义分类”的标准化归并能力
- 在 `L2 -> L4` 与 `L4 -> L6` 路径中优先复用已有稳定分类，减少新碎片分类继续产生
- 提供一个面向历史数据的手动收敛入口，将已有近义 `L3/L5` 缓慢收口
- 保证数据库分类、知识库目录、Markdown 文件路径三者保持一致
- 不把历史全量分类收敛默认塞进深度整理，避免重新拉高负载

## 非目标

- 不实现激进的语义聚类或“相似就合并”
- 不引入人工审核工作流或审批后台
- 不引入庞大的同义词词库管理系统
- 不在本次方案中调整前端分类管理入口结构
- 不改变 `L3/L5` 作为目录、`L4/L6` 作为 Markdown 文件的映射语义

## 总体方案

本次能力分为两部分：

- `实时归并`
- `历史收敛`

二者共用同一套“分类标准化判定逻辑”，但执行时机不同。

### 实时归并

- 在 `L2 -> L4` 生成 `L3` 分类时，先得到候选分类名
- 将候选分类名送入标准化归并层
- 若命中高置信已有分类，则直接复用已有分类名
- 若未命中，则保留清洗后的新分类名

同理：

- 在 `L4 -> L6` 生成 `L5` 分类时，使用同样逻辑进行归并

### 历史收敛

- 提供手动触发入口，单独扫描现有 `L3` 或 `L5`
- 识别出明显近义分类组
- 为每组选择一个“主分类”
- 将该组下属 `L4` 或 `L6` 统一迁移到主分类
- 删除冗余空分类
- 同步清理知识库空目录

## 核心原则

- 只合并“明显近义”的高置信场景，边界模糊时宁可不合并
- 不在前端展示层做假合并，归并结果必须真实落到数据库和文件系统
- 不将历史全量收敛默认并入日常深度整理，避免重新造成性能压力
- 分类迁移后必须同步更新导出文件和目录结构，不能只改数据库不改知识库

## 分类标准化判定

### 1. 文本清洗

标准化归并层先对候选分类做轻量清洗，得到“比较键”。

清洗范围只做格式去噪，不做主题改写，包括：

- 去除首尾空白和重复空格
- 统一中英文括号、连字符、下划线等轻微格式差异
- 对常见技术名统一大小写或稳定写法
- 去除弱区分尾词，例如“相关”“说明”“整理”“总结”
- 对少量稳定尾词做轻量归一，例如“流程/机制/方案/规范”

说明：

- 比较键只用于判断是否归并
- 最终展示名称优先复用已有稳定分类，不强制直接使用比较键

### 2. 明显近义定义

允许自动归并的情况：

- 主体词完全一致，仅尾词不同
- 主体词一致，仅是否带“自动化/机制/流程/方案/规范”等轻尾词不同
- 同一技术主题，仅有轻微命名差异但主干一致

不允许自动归并的情况：

- 虽然属于同领域，但关注点不同
- 一个偏“写入”，一个偏“同步”
- 一个偏“部署”，一个偏“运维”
- 一个偏“配置”，一个偏“权限”

### 3. 主分类选择

当多个候选都可作为保留名时，按以下优先级选择主分类：

1. 已被更多下层记忆使用的分类
2. 命名更短、更稳定、更通用的分类
3. 已存在知识库目录的分类

目标是让系统向稳定主类名收敛，而不是反复重命名。

## 服务边界

### `memory_service`

负责：

- 在实时分类生成路径中接入标准化归并
- 提供历史 `L3/L5` 收敛入口
- 执行 `L4/L6` 分类迁移
- 在收敛完成后触发现有空分类清理

### 新增 `category_normalization_service`

建议新增轻量服务，职责仅包含：

- 分类名清洗
- 比较键生成
- 明显近义匹配
- 主分类决策
- 输出归并建议结果

这样可以避免把现有 [memory_service.py](file:///Users/gengyun/Desktop/DiamondMemory/backend/app/services/memory_service.py) 继续堆大。

### `md_export_service`

负责：

- 分类迁移后的 Markdown 重新导出
- 空旧目录删除
- `file_path` 同步更新

## 实时归并接入点

### `L2 -> L4`

- 当前流程会通过 `_generate_category()` 生成候选分类
- 改造后，候选分类先进入 `normalize_category_name(candidate, layer=3)`
- 返回标准分类名后，再用于 `L4` 写入和 `L3` 目录骨架生成

### `L4 -> L6`

- 当前流程会通过 `_generate_skill_category()` 生成技能分类
- 改造后，候选技能分类先进入 `normalize_category_name(candidate, layer=5)`
- 返回标准分类名后，再用于 `L6` 写入和 `L5` 目录骨架生成

## 历史收敛流程

### 输入

- 目标层级：`L3` 或 `L5`
- 可选限制参数：单轮最多处理多少分类组

### 流程

1. 读取对应层级全部分类名
2. 生成比较键并做分组
3. 仅对“明显近义”的分组生成收敛计划
4. 为每组挑选一个主分类
5. 将组内其他分类下的 `L4` 或 `L6` 迁移到主分类
6. 对迁移后的目标记忆重新导出 Markdown
7. 删除空旧分类
8. 复用现有 `cleanup_empty_categories()` 清理空目录

### 输出

返回收敛结果摘要，包括：

- 识别到的近义分类组数量
- 实际完成迁移的 `L4/L6` 条数
- 删除的空 `L3/L5` 条数
- 删除的空目录数量

## 接口设计

建议新增一个手动后端入口，例如：

- `POST /api/memory/organize/categories/merge`

请求参数建议支持：

- `layer`: `3` 或 `5`，也可支持 `all`
- `max_groups`: 单次最多处理的近义组数量

返回结构建议包含：

- `status`
- `layer`
- `groups_detected`
- `groups_merged`
- `children_moved`
- `categories_deleted`
- `directories_deleted`

## 性能策略

- `实时归并` 只做轻量规则匹配，不调用大模型
- `历史收敛` 单独手动触发，不默认塞入深度整理
- 若后续历史收敛数据量变大，可沿用现有“低功耗分阶段慢跑”模式做批次限流

## 数据一致性要求

- `L4/L6.category` 必须写入最终标准分类名
- 分类迁移后，数据库中的 `file_path` 必须与新目录同步
- 冗余分类删除后，不应残留孤儿 Markdown 文件或空目录
- 现有 `L4/L6` 父级标签展示能力应自动受益于标准分类名，不需要额外补丁

## 测试策略

### 规则测试

- 测试明显近义会被正确识别
- 测试不明显近义不会误合并
- 测试比较键生成对尾词、空白、轻微格式差异稳定

### 服务测试

- 测试实时归并时，新分类会复用已有主分类
- 测试历史收敛时，`L4/L6` 会迁移到主分类
- 测试收敛后空旧分类会被删除
- 测试收敛后知识库目录会同步清理

### 回归测试

- 不影响现有 `L4/L6` 下行导出
- 不影响 `L4/L6` 父级标签展示
- 不影响分类管理弹窗中的分类删除和兜底迁移逻辑

## 实施顺序

1. 新增分类标准化服务
2. 接入实时归并到 `L2 -> L4` 与 `L4 -> L6`
3. 新增历史 `L3/L5` 收敛接口
4. 补充单元测试和服务测试
5. 后续再视需要决定是否为前端增加单独入口

## 风险与约束

- 分类归并若规则过宽，存在误合并风险，因此本次只做保守规则
- 历史收敛涉及文件迁移和重导出，必须确保文件路径同步更新
- 若旧分类已被用户人工理解为不同语义，自动合并会破坏认知，因此边界模糊场景必须跳过

## 结论

本方案采用“保守规则型明显近义归并”的方式，为 `L3/L5` 增加一层轻量分类标准化能力：

- 新数据在实时整理时优先复用稳定分类
- 老数据通过手动收敛入口逐步并回主分类
- 不引入激进语义合并，不重新拉高深度整理负载

该方案能在现有架构上较低风险地解决 `L3/L5` 越长越碎的问题。
