# 知识库实时文件树映射设计

## 背景

当前知识库左侧文件树直接读取用户存储目录中的真实文件和文件夹，因此“知识库中实时显示记忆里的 L3-L6”并不主要是预览页问题，而是后端下行导出语义与前端刷新时机的问题。

现状存在两个核心偏差：

- `L3/L5` 被当作普通记忆导出为 `.md`，而不是仅作为目录层存在
- 文件树主要依赖轮询刷新，导致记忆变更后不能立刻反映到知识库

## 目标

- `L3` 在知识库中只显示为 `总结经验/<分类名>/` 文件夹
- `L5` 在知识库中只显示为 `技能/<分类名>/` 文件夹
- `L4` 以 `.md` 文件实时显示在对应 `L3` 文件夹下
- `L6` 以 `.md` 文件实时显示在对应 `L5` 文件夹下
- 历史已有的 `L3-L6` 也能按新规则一次性补齐到知识库
- 记忆页发生影响 `L3-L6` 的操作后，知识库文件树立即刷新，不等待 5 秒轮询

## 方案

### 后端导出规则

- 扩展 `backend/app/services/md_export_service.py`
- `L3/L5`：
  - 只负责创建目录
  - 不再写出目录层 `.md`
  - 若历史存在同名旧 `.md`，一并清理
  - 清空这类记忆在数据库中的 `file_path`
- `L4/L6`：
  - 继续导出为 `.md`
  - 若分类或文件名变化导致路径变化，删除旧文件并写入新文件
  - 写入后同步更新 `file_sync`，避免上行同步把系统刚写出的文件再次重复摄取

### 全量补齐

- 新增一个后端入口，对数据库中所有 `L3-L6` 执行一次重建导出
- 重建过程遵循新语义：
  - 先补齐 `L3/L5` 目录
  - 再导出 `L4/L6` 文件
  - 清理可识别的历史 `L3/L5` 旧 `.md`

### 前端即时刷新

- 在前端定义统一的“知识库文件树刷新”事件
- `FileTree.vue` 监听该事件并立即重新读取当前目录
- `MemoryView.vue` 在成功创建、删除、整理完成、分类修改后主动触发刷新事件
- `App.vue` 在进入知识库页时调用后端重建导出入口，并在完成后触发一次刷新事件

## 边界处理

- `L4` 分类缺失时导出到 `总结经验/未归档/`
- `L6` 分类缺失时导出到 `技能/未分类/`
- 仅调整系统生成的 `L3-L6` 文件树语义，不改变用户手工创建 Markdown 的展示方式
- 删除 `L3` 时，现有 `L4 -> 未归档` 迁移逻辑继续保留
- 删除 `L5` 时，补齐对应 `L6 -> 未分类` 的迁移与旧目录清理

## 验证

- 进入知识库页后，历史 `L3/L5` 只显示文件夹，历史 `L4/L6` 显示为 `.md`
- 新建或整理产生新的 `L3-L6` 后，知识库文件树立刻出现最新结构
- 删除 `L4/L6` 后，对应 `.md` 立刻消失
- 删除 `L3/L5` 后，旧目录按迁移规则正确更新
- 上行同步不会把系统刚导出的文件重复创建成新记忆
