# L3-L6 下行同步到知识库设计

## 背景

当前知识库侧边文件树直接读取用户存储目录中的文件夹与 Markdown 文件，因此要让 L3-L6 内容稳定展示到知识库，关键不在前端，而在后端是否能把数据库中的 L3-L6 记忆持续、正确地下行到 `总结经验/` 和 `技能/` 目录。

现状存在以下问题：

- `L3-L6` 在部分创建路径上会触发导出，但调用点分散，缺少统一协调。
- `update_memory()` 未统一触发重导出，内容修改后文件侧不一定更新。
- `delete_memory()` 仅部分处理目录删除，文件删除与同步记录清理不完整。
- 现有下行和上行都围绕知识库目录工作，但没有明确的“系统写回后不再被自己上行重复摄取”的闭环。
- 历史数据库中的 `L3-L6` 未保证已完整补齐到知识库目录。

## 目标

- 将数据库中的 `L3-L6` 记忆实时下行到知识库目录。
- `L3/L5` 以文件夹承载，不额外生成目录层索引 Markdown。
- `L4/L6` 以 Markdown 文件承载，分别落在 `总结经验/` 与 `技能/` 目录下。
- 首次上线时支持对已有 `L3-L6` 做一次全量补齐。
- 系统下行写入后，不会被上行同步误判为新的用户文件再次摄取。
- 用户手动编辑系统生成的 Markdown 后，仍能通过现有上行机制回写数据库。

## 非目标

- 不修改前端知识库展示结构。
- 不引入新的目录层 Markdown 索引页。
- 不改变现有“用户手工知识文件”的上行入口与编辑方式。
- 不处理 L1/L2 直接导出到知识库的需求。

## 存储路径切换交互

切换存储位置属于受控操作，不应被界面识别为后端异常断开。该交互规则适用于本次下行同步能力，因为切换存储目录后，系统需要在新目录中继续维护 `总结经验/` 与 `技能/` 的映射结构。

### 目标

- 用户切换存储位置后，系统在后台自动完成后端重启
- 切换期间不出现“服务已断开”全屏弹窗
- 仅显示轻提示 `正在切换存储路径并重启服务...`
- 重启成功后自动刷新知识库路径和文件树
- 若重启失败，优先在设置页提示失败，而不是直接进入全局断开态

### 交互规则

- 存储路径切换触发的后端重启定义为“受控重启”
- `App.vue` 中全局断开弹窗在“受控重启中”必须被抑制
- `SettingsView.vue` 发起切换后应进入 `storagePathChanging` 状态
- 在该状态结束前，界面仅展示轻提示，不弹全局异常遮罩
- 后台流程应为：保存新路径 -> 初始化目录 -> 重启后端 -> 健康检查通过 -> 刷新前端状态
- 若受控重启失败，设置页显示明确失败信息；只有退出受控状态后且后端仍不可用，才允许进入全局断开逻辑

## 目录映射规则

### 目录层

- `L3` 映射为 `总结经验/<分类名>/`
- `L5` 映射为 `技能/<分类名>/`
- `L3/L5` 只承载为文件夹，不额外生成 `.md`

### 内容层

- `L4` 映射为 `总结经验/<分类名>/<文件名>.md`
- `L6` 映射为 `技能/<分类名>/<文件名>.md`
- `L4/L6` 继续使用现有 frontmatter，并保留 `memory_id`

### 兜底规则

- `L4` 若分类缺失，则落到 `总结经验/未归档/`
- `L6` 若分类缺失，则落到 `技能/未分类/`
- 若目录层尚未存在，系统先补建目录，再写文件

## 架构设计

### 统一下行协调层

新增统一的下行协调能力，职责是将数据库中的 `L3-L6` 映射到知识库文件系统。实现上优先扩展现有 `backend/app/services/md_export_service.py`，避免重复分散逻辑。

该协调层负责：

- 计算目标目录与文件路径
- 创建或重命名 `L3/L5` 目录
- 写入或覆盖 `L4/L6` Markdown
- 删除失效文件或目录
- 在系统写入后同步更新 `file_sync_info`
- 提供一次性全量补齐/重建入口

### 服务边界

- `memory_service` 负责记忆生命周期变更
- `md_export_service` 负责下行文件系统映射
- `knowledge_service` 继续负责上行扫描与文件读取，不承担下行编排

## 触发点设计

以下场景统一调用下行同步：

- `create_memory()` 创建 `L3-L6`
- `update_memory()` 更新 `L3-L6`
- `delete_memory()` 删除 `L3-L6`
- `L2 -> L4` 提炼产生新 `L3/L4`
- `L4 -> L6` 提炼产生新 `L5/L6`
- 去重、合并、重分类导致的 `L3-L6` 变更
- 切换存储目录后执行一次全量重建

### 实时同步要求

- 新建 `L3/L5`：立即建目录
- 新建 `L4/L6`：立即写文件
- 更新 `L4/L6`：立即覆盖文件内容
- 更新 `L3/L5`：必要时重命名目录，并修正其下系统文件路径记录
- 删除 `L4/L6`：立即删文件并清理同步记录
- 删除 `L3/L5`：立即删空目录，或在业务允许的迁移逻辑完成后清理旧目录

## 上下行防冲突设计

### 核心原则

- 系统下行写出的 Markdown 仍然是可编辑的
- 用户手改系统文件时，应更新回对应数据库记忆
- 系统自己写出的文件，不应被上行再次当成“新文件”创建新记忆

### 实现方式

- 下行文件保留 `frontmatter.memory_id`
- 下行写入后，立即更新 `file_sync_info(relative_path, mtime, hash)`
- 上行扫描发现 `memory_id` 存在时：
  - 若文件 hash 未变化，直接跳过
  - 若文件 hash 已变化，认定为用户修改系统文件，更新对应记忆内容
- 删除系统文件时，同时删除对应 `file_sync_info`
- 全量补齐时仅清理“带 `memory_id` 但数据库中已不存在对应记忆”的系统文件
- 对没有 `memory_id` 的用户自建文件，不做删除或覆盖

## 全量补齐策略

新增一次性重建入口，执行顺序如下：

1. 扫描数据库全部 `L3-L6`
2. 先确保 `L3/L5` 目录存在
3. 再按当前数据库内容重写全部 `L4/L6` 文件
4. 清理知识库中失效的系统文件
5. 清理因分类迁移产生的失效空目录
6. 刷新对应的 `file_sync_info`

### 清理范围

- 仅处理 `总结经验/` 与 `技能/` 下系统生成内容
- 仅清理能通过 `memory_id` 判定为系统文件、且数据库中已无对应记忆的文件
- 不清理用户手工创建、无 `memory_id` 的 Markdown

## 文件命名与路径策略

- 继续沿用现有标题提取与文件名清洗逻辑
- 若文件重名，允许在导出层追加稳定去重后缀，避免覆盖其他记忆
- 数据库中的 `file_path` 必须与最终写入路径一致
- 当分类变化导致路径变化时，同步更新数据库 `file_path`

## 失败处理

- 单条记忆下行失败时，记录日志，不阻断整批处理
- 全量补齐返回成功数、失败数和失败明细
- 写文件前确保目标目录存在
- 重命名目录或文件时，若目标已存在冲突项，按系统文件优先规则进行可预测处理，不覆盖用户无 `memory_id` 文件

## 验证方案

### 功能验证

- 历史数据库中的 `L3-L6` 执行一次全量补齐后，能立即在知识库树中看到 `总结经验/技能` 内容
- 新增 `L4/L6` 后，知识库目录立即出现对应 `.md`
- 修改 `L4/L6` 内容后，对应文件立即更新
- 修改 `L4/L6` 分类后，对应文件迁移到新目录
- 删除 `L4/L6` 后，对应文件立即删除
- 删除或迁移 `L3/L5` 后，目录结构正确更新

### 一致性验证

- 系统下行写完后，上行扫描不会重复创建新记忆
- 用户手动编辑系统生成的 Markdown 后，数据库对应记忆会更新
- 用户手工文件不会被全量补齐误删

## 代码落点

- `backend/app/services/md_export_service.py`
  - 扩展为统一下行协调中心
  - 增加目录创建、路径计算、全量补齐、同步记录刷新能力
- `backend/app/services/memory_service.py`
  - 在 `L3-L6` 生命周期变更处统一调用下行能力
  - 补齐 `update/delete/merge/reclassify` 等漏掉的同步点
- `backend/app/services/knowledge_service.py`
  - 维持上行扫描
  - 复用 `file_sync_info`，避免上下行互相打架
- 可选新增 API
  - 提供手动触发“全量下行补齐/重建”的接口，供设置页或运维入口调用

## 风险与约束

- 现有 `memory_service` 中部分逻辑直接调用旧导出接口，迁移时需要统一收口，避免重复导出
- 目录重命名会影响已有 `file_path`，必须保证数据库与文件系统同时更新
- 文件重名策略若不稳定，可能导致路径抖动，因此应使用可预测规则
- 上行扫描当前以 `mtime + hash` 为主，系统写入后必须及时刷新同步记录，否则会被自己重新摄取

## 推荐实施顺序

1. 统一封装下行路径与目录映射规则
2. 补齐 `create/update/delete` 的实时同步闭环
3. 增加全量补齐/重建入口
4. 接入整理、去重、重分类等批处理流程
5. 增加针对上下行互斥和历史补齐的测试

## 结论

本方案采用“统一下行协调层 + 一次性历史补齐 + 持续实时同步”的方式，将 `L3/L5` 映射为知识库目录，将 `L4/L6` 映射为 Markdown 文件，并通过 `memory_id + file_sync_info` 与现有上行同步形成闭环，满足 V0.8 对知识库实时展示与双向同步的要求。
